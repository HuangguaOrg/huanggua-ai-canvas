# 打包与发版流程

> 适用于已启用 `createUpdaterArtifacts`、自动更新和 GitHub Actions 质量门禁的版本。
> 当前版本以 `package.json` 为唯一来源，不在本文档中固定具体版本号。

## Windows 客户端增量更新

用户打开「关于 → 检查更新」。已安装的黄瓜 AI 画布 Windows x64 NSIS 版通过 HTTPS 443 直接读取 Gitee 公开更新源 `https://gitee.com/xiang834740239/huanggua-aiagent/raw/master/latest.json`（兼容回退 `raw/main/latest.json`，国内用户无需访问 GitHub）。客户端无需开放入站端口，只有正式渠道公布了更高版本，客户端才会提示下载，默认增量包下载地址为 `https://gitee.com/xiang834740239/huanggua-aiagent/releases/download/v<版本>/HuangGuaAI-<版本>-windows-x64-update.exe`。

发布采用「**首发完整包放网盘/官网，日常增量在线更新放 Gitee**」方案：
- 新用户首次安装下载完整安装包（`黄瓜 AI 画布_<版本>_x64-setup.exe`，约 300+ MB，通过网盘或官网分发）；首发基线版本（`0.11.7`）在 Gitee 仓库根目录仅提交 1 KB 的 `latest.json` 作为增量对比基线（可用 `--baseline-manifest-only` 生成）。
- 后续日常版本（`0.11.8+`）生成 `HuangGuaAI-<版本>-windows-x64-update.exe`（不改动短剧与导演台大归档时仅约 15–25 MB）、对应的 `.sig` 和 `latest.json`，通过 `GITEE_TOKEN=<令牌> python scripts/publish-gitee-update.py --dir <输出目录>`（或手动上传至 Gitee Release 并更新仓库根目录 `latest.json`）完成发布。增量包在覆盖前逐个核验本机复用资源的 SHA-256；若本机缺失或修改了复用文件，提示用户使用完整安装包修复。

### 短剧运行时：单归档分发与首次解压（0.11.7 起）

- 打包源仍是 `src-tauri/resources/huanggua-studio/`（逐文件 SHA-256 清单，`release:preflight` 校验）。`scripts/package-studio-runtime.py` 会精简从未被引擎导入的内容：火山 SDK 只保留 `volcenginesdkcore`、`volcenginesdkark`、`volcenginesdkarkruntime`，并去掉 `python/tcl`、`python/include`；已暂存的运行时可用 `--prune-existing` 重新应用。文件数由约 40,400 降到约 14,000。
- `npm run release:pack`（`scripts/pack-studio-runtime.py`）把暂存目录打成可重现的 `huanggua-studio.zip` 与说明文件 `huanggua-studio.json`，NSIS 只安装这两个文件。`build.rs` 把归档与清单摘要编译进主程序。
- 客户端启动后在后台把归档解压到 `%LOCALAPPDATA%\com.huanggua.canvas\huanggua-studio-runtime\<摘要前 16 位>\`：清单须与编译期摘要一致，每个文件按清单逐一核验后才原子切换目录；该目录登记为应用私有路径，Renderer 的路径命令不可读写。卸载时一并删除；从旧版平铺目录升级时安装器一次性清理 `$INSTDIR\huanggua-studio`。
- 增量更新的固定基线记录在 `runtime/studio/update-baseline.json`（首个单归档版本的资源摘要，用 `--write-baseline` 生成）。基线版本本身以完整安装包作为更新包；之后的版本由 `python scripts/build-incremental-update.py --installer-script <installer.nsi> --full-installer <setup.exe> --out <新目录>` 生成增量包，归档未变化时不随包重发。从第二次增量发布起读取上一次正式清单的 `carriedResources`，支持跳版本和内容回退；离线演练可用 `--previous-feed`。已发布资源被删除时工具中止，要求先补齐清理逻辑。对外发布前，在独立 Windows 测试账户演练旧版升级、重启与项目恢复。


## macOS 的 Gitee 应用内更新（0.11.11 起）

0.11.10 及以前的 macOS 包关闭了更新源，用户需要手动安装一次 0.11.11 或更新的完整 DMG；启用后的客户端通过「关于 → 检查更新」安装后续版本。发布后的稳定标签和安装包不能为此改写。

Mac 继续使用 Tauri 的完整 `.app.tar.gz` 更新格式和安装器。Gitee 单附件上限为 100M，因此 `scripts/build-macos-update.py` 将归档分为最多 90 MiB 的有序分片，并用同一个更新器密钥分别签名。另生成签名的 `.update.json` 描述文件，绑定版本、平台、每片地址、签名、长度、SHA-256 以及完整归档哈希。`latest.json` 的 `darwin-aarch64` 项指向该描述文件，签名字段也是描述文件的签名。

`app_update.rs` 先通过原生 updater 验证描述文件，再验证每个分片；只允许当前版本在固定黄瓜 Gitee 仓库下的对应附件地址。所有分片完整、有序且总哈希一致后才停止运行时并交给原 Tauri 安装器。下载、验签、缺片或内容校验失败均不启动安装。Windows 的签名增量安装路径保持原样。

Mac 工作流启用 `createUpdaterArtifacts`，复用 `TAURI_SIGNING_PRIVATE_KEY`，保留完整 DMG；签名分片通过 `macos-update-<架构>-<SHA>` Actions artifact 交给发布端。工作流只创建草稿，不自行公开未齐全的多平台发行版。发布时可使用：

```powershell
python scripts/publish-gitee-update.py --dir <Windows更新目录> --macos-dir <Mac分片目录>
```

发布工具先验证本地文件关系，上传 Mac 分片及描述文件，全部成功后才把 Mac 平台合入共享更新清单。同名附件通过完整下载哈希校验后才可复用，内容不同则拒绝覆盖。公开前分别核对 Windows 增量包、Mac 描述文件和所有分片的签名、哈希、公开地址与目标版本。Mac 仍采用 ad-hoc 代码签名，和更新包的密码学签名分别管理。

验证入口：`scripts/test_macos_update.py`、`app_update_multipart.rs` 的内联测试、前端更新与准备流程回归，以及真实 Mac 的签名构建。发布后在可丢弃项目中验证手动安装启动、检查后续版本、下载安装重启与项目恢复；本机没有 Mac 图形界面时，应明确保留该交互验收缺口。

## 前置准备

### 需要的文件 / 配置

| 文件 | 作用 |
|---|---|
| `package.json` → `version` | 前端版本号（唯一来源） |
| `src-tauri/tauri.conf.json` → `version` | Tauri 版本号，运行时读取 |
| `src-tauri/Cargo.toml` → `package.version` | Rust 编译版本号 |
| `src-tauri/update-key.key` | 签名私钥（**敏感，勿提交**） |
| `src-tauri/update-key.key.pub` | 签名公钥（已写入 `tauri.conf.json` 的 `plugins.updater.pubkey`） |
| `src-tauri/tauri.conf.json` → `bundle.createUpdaterArtifacts` | 设为 `true`，构建时生成 `.sig` 签名文件 |
| `.github/workflows/ci.yml` | 正式版本标签打包时按风险选择相关／全量源码检查，保留完整类型检查和生产构建，Rust 预检按计划执行；普通推送和 PR 不启动源码 CI |
| `.release-notes.md` | 当前版本的 Release notes 审阅稿；每次发版覆盖，历史版本由 Git 记录保留 |
| `.github/release-title.txt` | 一行完整 Release 名称，版本须与目标标签和 `package.json` 一致 |
| `.github/workflows/release.yml` | Tag 转交默认分支发布、同 SHA 门禁与产物核验；Windows、macOS 两个标准平台与 Windows Legacy 并行，全部成功后公开 |

### GitHub Secrets（无需每次修改）

在仓库 **Settings → Secrets and variables → Actions** 中配置：

| Secret | 值 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `update-key.key` 文件内容（一行 `dW50cnVzdGVk...`） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成密钥时设置的密码 |

> 密钥通过 `npx tauri signer generate -w ./src-tauri/update-key.key -f -p "<签名密码>" --ci` 生成。
> 每次重新生成密钥后，必须连同 `tauri.conf.json` 中的 `pubkey` 一起更新。
> 私钥、签名密码和包含它们的终端输出不得提交到仓库或写入发版记录。

### macOS 临时签名与首次打开

后续版本的 macOS 安装包仅发布 M 系列芯片（Apple Silicon）的 `aarch64-apple-darwin` 目标，不再构建或发布 `x86_64-apple-darwin`；已发布的历史安装包保留。

当前 GitHub 发布工作流为 Apple Silicon 安装包设置 `APPLE_SIGNING_IDENTITY=-`，由 Tauri 在打包前完成应用和所包含代码的临时签名（ad-hoc）。无需配置六个 `APPLE_*` Secret，也不执行 Apple 公证和票据装订。上表中的 Tauri 更新器密钥仍用于生成 `.sig`，与 macOS 代码签名分别管理。临时签名配置见 [Tauri 的 macOS 签名说明](https://v2.tauri.app/distribute/sign/macos/#ad-hoc-signing)。

macOS 任务验证签名完整性和 `Signature=adhoc`，随后在 GitHub macOS runner 上尝试启动应用。所有平台任务成功后才将 Release 草稿公开。该检查只验证 runner 上的签名和启动，不能代表浏览器下载后通过 Gatekeeper；发布后仍需在另一台 Mac 上下载 `.dmg`，核对安装和首次打开。

浏览器下载可能添加 `com.apple.quarantine` 隔离属性，构建时清除该属性无法阻止下载时重新添加。临时签名包没有 Apple 公证，安装到「应用程序」后首次打开可能被拦截，可在「系统设置 → 隐私与安全性」中选择「仍要打开」。若提示应用已损坏，确认下载的是本仓库发布包后，可在本机终端运行：

```bash
xattr -dr com.apple.quarantine "/Applications/AI Canvas.app" && open "/Applications/AI Canvas.app"
```

该命令仅清除指定应用的下载隔离属性并打开应用，不重新签名；安装路径不同则替换应用路径。首次打开方式见 [Apple 的说明](https://support.apple.com/zh-cn/102445)。如以后恢复 Developer ID 签名和 Apple 公证，需要重新接入证书、公证凭据及相应 CI 校验。

## 第一步：版本号同步

### 1.1 修改 `package.json` 的 `version`

例如将当前版本 `X.Y.Z` 更新为目标版本，并确保符合语义化版本规则。

### 1.2 运行同步脚本

```powershell
npm run sync-version
```

这会自动同步版本号到：
- `src-tauri/Cargo.toml`（Rust 编译时不再显示旧版本）
- `README.md`（版本 badge）

同步脚本当前不会更新其他语言 README、站点或说明书。还需核对：

- `README.en.md`、`README.ja.md`、`README.ko.md` 的版本徽章与核心能力；
- `site/index.html` 的版本及下载文案；
- `site/manual.html` 的标题、版本、核对日期、正文操作入口和截图说明；
- `site/README.md` 的维护流程，以及受影响的当前模块文档；
- `package-lock.json` 的根版本与 `packages[""].version`，以及 `src-tauri/Cargo.lock` 的应用包版本（不改依赖解析结果）。

说明书可以记录后续源码功能，但必须明确区别于当前发布包，不能仅把版本号替换后宣称新功能已发布。纯文档更新检查链接、UTF-8、脚本和图片完整性；实际发布仍执行后面的质量门禁。

四份 README 的版本徽章应同步核对，能力正文只在对应修改获得授权时调整。更新当前架构文档时，从 `useAppStore.ts` 核对 slice 清单、从 `indexedDb/schema.ts` 读取 `DB_VERSION`；历史测试结论不改写为本次通过。最新准备见[v0.11.6「全页剧本工作台与大纲资料」](./plans/2026-11-15-release-0.11.6.md)，以已公开 v0.11.5 为基准。源码 CI 与标准／Legacy 构建固定 Rust 1.99.1，当前 ONNX 依赖尚未适配 Cargo 1.100 的中间目录变化，升级工具链前须核对 DLL 复制与打包。实际门禁与发布证据留在 Actions Summary，不为补成功流水重新触发门禁。历史见[发布记录](./发布记录.md)，文档维护从[导航](./文档导航.md)与[专项索引](./plans/计划索引.md)进入。

### 1.3 手动修改 `src-tauri/tauri.conf.json`

```json
"version": "X.Y.Z"
```

> 三处版本号（`package.json`、`tauri.conf.json`、`Cargo.toml`）必须一致。

## 第二步：编写 Release notes（发布说明）

Release notes（发布说明）面向安装或升级应用的人，说明本次更新的用户价值、兼容性影响和安装包选择。正文只维护 `.release-notes.md`，标题只维护 `.github/release-title.txt`，工作流从目标标签源码读取，不在 YAML 中重复抄写。

### 2.1 确认事实来源

以最近一个正式 Tag 为比较基准，检查该 Tag 到当前 `HEAD` 的提交和文件差异：

```powershell
$previousTag = "vX.Y.Z"
git log --oneline "$previousTag..HEAD"
git diff --stat "$previousTag..HEAD"
git diff --name-status "$previousTag..HEAD"
```

编写时遵守以下规则：

- 每项更新必须能追溯到提交、代码差异或已通过的测试
- 不根据计划文档、未合并分支或未完成代码推测发布内容
- 不直接复制提交列表，应合并重复提交并转换为用户可理解的结果
- 纯文档、测试和内部重构通常不进入正文，除非它们改变用户行为或兼容性
- 上一版本仍然存在的平台限制必须继续说明，不能因本次未修改相关代码而省略

### 2.2 组织标题和正文

Release 名称使用 `AI Canvas vX.Y.Z - 版本主题`。版本主题应概括最重要的用户变化，避免使用“体验优化”“问题修复”等无法区分版本的泛化表述。

正文按以下顺序组织：

1. **版本摘要**：用 1 至 2 句话说明核心价值，不重复罗列所有条目
2. **主题分组**：按角色库、画布、对话助手、媒体生成等用户任务分组，通常保留 2 至 4 组
3. **升级与兼容性**：存在数据迁移、行为变化、功能缺失或平台限制时必须添加
4. **下载说明**：列出当前实际生成的 Windows、macOS 安装包（Linux 暂停构建，用户明确要求后再恢复）

每个条目只表达一个可验证的变化。优先使用“新增”“支持”“优化”“修复”“调整”等明确动作，并写出变化对象和结果。不要使用“若干优化”“提升稳定性”“改善体验”等缺少事实范围的描述。

以下内容必须在适用时写入：

- 破坏性变更、配置重置、数据迁移和不可逆操作
- 厂商、模型、计费方式或所需 API Key 的变化
- 操作系统、CPU 架构和本地运行时限制
- 已知问题及可执行的规避方式

不得写入 API Key、签名私钥、完整本地路径、内部调试日志或未公开的服务地址。

### 2.3 使用固定模板

更新根目录下固定的 `.release-notes.md`，每次发版直接覆盖上一版正文，历史内容由 Git 记录保留。正文使用以下模板。没有兼容性内容时，删除整个“升级与兼容性”小节，不保留空标题。

```markdown
## ✨ 版本摘要

release_summary_here

## feature_theme_here

- user_visible_change_here

## ⚠️ 升级与兼容性

- compatibility_or_limitation_here

## 📦 下载

- 🪟 Windows：使用 `.exe` 或 `.msi`。
- 🍎 macOS：仅提供 M 系列芯片（Apple Silicon）的 `aarch64.dmg`，不再发布 Intel 安装包。
- Linux：暂停构建安装包，历史版本保留，恢复须由用户明确提出。
```

主题标题可以使用一个与内容匹配的图标。正文条目不添加装饰图标，避免影响扫描。

### 2.4 核对标题与目标源码

审阅 `.release-notes.md` 后，核对 `.github/release-title.txt` 与目标源码：

- 标题完整使用 `AI Canvas vX.Y.Z - 版本主题`，只有一行，主题与正文一致
- 正文与版本资料使用同一个 `X.Y.Z`，不需要改写工作流正文
- 标题、正文、五份版本文件与标签一起进入同一提交；默认分支编排不能误用其最新版本文案替代目标标签的文案
- 下载说明与构建矩阵实际生成的产物一致

在 Tag 推送前完成文案同步。已公开版本的 Tag、Release 和安装包不得改写；发现代码或文案问题应另发补丁。尚未公开的版本仅在用户明确要求继续同一版本时，按[未公开同版本续发](#未公开同版本续发)处理，不能仅因已经推送标签就擅自增加版本号。

### 2.5 Release notes 检查清单

创建发版提交前逐项确认：

- [ ] 比较范围从上一正式 Tag 到当前 `HEAD`
- [ ] 每条内容都能追溯到代码差异或测试结果
- [ ] 标题和摘要说明本次版本的主要用户价值
- [ ] 内部实现细节已转换为用户可理解的行为变化
- [ ] 数据迁移、平台限制和已知问题没有遗漏
- [ ] 工作流从目标标签读取 `.release-notes.md`，不另维护一份 YAML 正文
- [ ] Release 名称、正文和版本文件使用同一个版本号
- [ ] 下载说明与当前构建矩阵一致
- [ ] 文案不包含密钥、完整本地路径或内部日志
- [ ] 文件通过严格 UTF-8 解码和乱码扫描

## 第三步：质量门禁

源码 CI 只在正式版本标签发起打包时远端执行，普通分支推送和 PR 不启动源码 CI；官网／演示自动构建部署保留。`pre-push` 对所有推送均不安装依赖或运行检查，本地验证需用户明确授权。打包先从可信完整检查成功的严格祖先累计全部未验证改动，冻结目标／基线 SHA、检查模式和实际文件清单：普通改动执行相关检查，高风险、无基线或范围不可靠时全量。所有模式保留完整类型检查、真实生产构建及新前端产物；同标签、同 SHA、同次尝试的真实检查证明通过后才允许构建安装包。标签可与 `master` 同批原子推送，但不是打包或公开已成功的证明。失败或缺少可信证明时停止发布。

### 3.1 前端检查

```powershell
npm run ci
```

`npm run ci` 当前依次执行：

- 全仓 ESLint（零告警）；
- 前端生产代码类型检查；
- 测试代码类型检查；
- Vitest 自动化测试。
- 前端生产构建。

上述命令是用户显式需要本地全量检查时的入口，普通提交和推送不会自动执行。正常发版由标签触发远端按风险规划的门禁，本地不再重复执行。`affected` 模式仅筛选 lint／测试范围，应用和测试类型、生产构建不省略。需要重装依赖时单独运行 `npm ci`；不增加按 HEAD 或时间戳猜测成功的本地缓存，也不为发版删测试、扩大超时或直接开启全量并行。

> lint 是发布计划和显式本地检查的必过门禁：`full` 检查全仓，`affected` 检查冻结清单中的文件。`eslint.config.js` 排除 Rust 构建产物、原生生成目录、vendor 和独立宣传视频项目；检查失败须修复，不跳过或降级依赖来掩盖错误。

### 3.2 Rust 检查

自动发布以同 SHA 源码 CI 的 `Rust check` 汇总结果为准。`full` 或存在原生影响时执行计划要求的原生检查；没有原生影响的 `affected` 可明确省略预检矩阵，不能将未执行伪装成已验证。安装包仍在实际平台编译和校验。以下命令只在已获授权的本地排查或构建验证中使用：

```powershell
Set-Location src-tauri
cargo check --lib --locked
cargo test --lib --locked native_project_media::tests::windows_media_
Set-Location ..
```

### 3.3 CI 检查

普通 `master`／其他分支推送和 Pull Request 不自动启动源码 CI，独立 GitHub Pages 官网／演示自动构建部署继续保留。只有推送稳定 `vX.Y.Z` 版本标签发起打包时，`.github/workflows/ci.yml` 自动执行：

1. 校验稳定标签和源码身份，标签提交必须属于同仓库默认分支历史；查找最近可信完整 CI 成功的严格祖先，累计其后的全部改动。仅比较最后一次提交会漏掉尚未检查的改动，不可作为发布范围依据。旧默认分支或新标签的完整证明可用，增量成功不是全量基线；较新失败或取消也不能借旧成功替代。
2. 生成冻结计划，记录目标／基线 SHA、`full`／`affected`、Rust 范围、lint 和实际测试文件。普通组件、服务、词条和可分类领域类型执行相关测试及显式源码读取回归；仅应用版本字段经前后精确比较可豁免高风险，依赖／锁解析结果、权限、凭据、持久化、全局入口、构建／测试基础设施或无法可靠判断的变化仍全量。无可信基线或查询／解析失败同样全量并说明原因。
3. `full` 完整执行前端 lint、四个 Vitest 分片和三平台 Rust；`affected` 只执行冻结的 lint／测试，预检 Rust 按计划选择。两种模式都执行应用／测试类型检查、完整生产构建，生成当前 SHA 的新前端产物。执行任务复核计划身份和路径，不重算或静默更换模式。
4. 上传 `frontend-dist-<SHA>-<运行尝试号>`。质量证明分别为 `Full source quality` 或 `Affected source quality (<baseSHA>)`；Summary 展示实际模式、基线、原因和范围，完整清单随同次计划产物保留。

Release gate 由默认分支固定工作流执行，核验当前同仓库、同正式标签、精确 SHA、同一次尝试的真实质量证明、`Frontend quality`、`Rust check` 和前端产物。增量模式另复核基线为严格祖先且具有可信完整 CI 成功记录，不能把增量结果标为全量成功。缺失、失败、取消、超时或模式／产物不符均阻止打包。产物缺失或过期时使用 GitHub 的 “Re-run all jobs” 重跑对应标签 CI。同一版本资料与标签应来自一次原子推送，普通分支推送不会额外启动源码 CI。首次采用本规则时可能因规则变化或无基线全量，后续仅版本元数据更新不会一律全量；验收见[发布加速专项](./plans/2026-11-07-release-acceleration.md#当前触发规则2026-11-15)。

## 第四步：本地构建（可选）

自动发布通常跳过本节与手动 `latest.json` 步骤，统一由 Actions 打包和签名。仅在明确需要本地安装包或本地排查时执行，不与远端打包机械重复。

### 4.1 设置环境变量

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = (Get-Content "src-tauri/update-key.key" -Raw).Trim()
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "<签名密码>"
```

> `Get-Content -Raw` 读取文件内容，`.Trim()` 去除尾随换行符，防止 base64 污染。
> `<签名密码>` 替换为生成密钥时设置的密码，不要把真实密码写入脚本或文档。

### 4.2 构建

```powershell
npm run tauri build
```

构建完成后产物位置：

```
src-tauri/target/release/bundle/
├── nsis/
│   ├── AI Canvas_X.Y.Z_x64-setup.exe      ← 安装包
│   └── AI Canvas_X.Y.Z_x64-setup.exe.sig  ← 签名文件
├── msi/
│   ├── AI Canvas_X.Y.Z_x64_en-US.msi
│   └── AI Canvas_X.Y.Z_x64_en-US.msi.sig
└── ...
```

### 4.3 检查产物

确认以下文件均已生成：
- `.exe` / `.msi` 安装包
- 对应的 `.sig` 签名文件
- 终端无报错

## 第五步：创建 `latest.json`

在 Windows 标准版完成打包后，按本文开头的增量更新命令生成清单与签名包。发布工作流使用同一脚本生成三个配套文件并附到草稿。首次安装用的完整安装包单独提供。

核验清单中的版本、`https://gitee.com/xiang834740239/huanggua-aiagent` 下载地址和增量包签名。保留额外的 `huangguaDelta` 字段供下次构建判断哪些文件需要随包分发。Gitee 更新托管仓库须保持公开，以便客户端无需登录直接通过 HTTPS 读取 `latest.json` 及其指向的签名更新包。

## 第六步：发布 GitHub Release

### 方式 A：自动发布（推荐）

```powershell
git status --short
git add <本次发版文件>
git commit -m "chore(release): 发布 vX.Y.Z"
# 在 master 上，确认版本资料与标签指向同一提交
git tag -a vX.Y.Z HEAD -m "vX.Y.Z 版本主题"
git push --atomic origin master refs/tags/vX.Y.Z
```

版本号、说明、模块资料先一次准备并提交，代码和标签一次原子推送，保证标签对应的源码与发布资料同时可用。普通推送不执行源码 CI；正式标签启动一次远端按风险规划的门禁，本地不重复运行。不要仅为补写一条成功流水再提交、推送一次；源码 SHA、模式、基线、清单与产物来源由 Actions Summary 留证，必要的后续文档修订合并到下一批授权推送。

推送 tag 后，`.github/workflows/release.yml` 自动触发：

1. 标签运行只转交发布请求；实际发布从仓库默认分支启动，始终检出目标标签的固定 SHA。手动启动也须在默认分支，并明确填写目标标签；不修改正在执行的旧版工作流。
2. `quality` 等待同标签、目标 SHA 的源码 CI，核验同一次尝试的真实全量／增量证明、前端／Rust 汇总和制品来源；增量另核验可信完整基线。失败、缺失、取消、超时或模式不符停止。
3. 下载并校验这份 CI 前端产物，使用固定发布配置复用前端并准备 MCP 适配器；普通本地构建保持原流程。
4. Windows、macOS 两个标准平台和 Windows Legacy 同时构建，各自使用隔离的 npm／Rust 缓存；Legacy 不等待标准包完成再开始。macOS 临时签名和启动检查保留。
5. 标准包生成 `.sig`、`latest.json` 与 Release 草稿；Legacy 先保存到 Actions 产物。最后任务等待所有平台验证成功，再上传 Legacy 并公开 Release。

实际发布放在默认分支是为了让不同版本复用原生缓存：GitHub 限制不同标签之间直接互读缓存。构建仍固定到目标标签，不以默认分支最新源码代替；首次冷缓存和工具链变化仍可能较慢。详见[发布加速专项](./plans/2026-11-07-release-acceleration.md)与[GitHub 缓存限制](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)。

#### 自动发布的交付节点：平台构建启动后无需继续等待

当同一发布提交满足以下条件时，助手即可结束本轮等待并向用户交付版本号、Tag 和 Actions 工作流链接：

- 同一次尝试的 `CI / Frontend quality`、`CI / Rust check` 及计划对应的 `Full source quality` 或 `Affected source quality (<baseSHA>)` 已成功，增量基线已通过 Release gate 独立复核；
- 默认分支实际发布运行的 `Release / Quality gate` 已成功，并在 Summary 标明目标标签和源码 CI；
- 两个 `Release / Publish` 平台任务（Windows、macOS Apple Silicon）均已启动，显示 `In progress`，且没有失败或取消。

此时 GitHub 总状态仍可能显示 `Some checks haven't completed yet`，属于安装包构建中的正常状态。无需持续轮询，也无需等待全部安装包、Windows Legacy、签名上传和最终公开完成；后续由 Actions 按既有依赖顺序自动执行。不额外创建定时监控，除非用户明确要求继续跟进。

交付时应明确写“发布构建已启动，后台自动完成”，不能写“安装包已发布完成”。最终公开仍以工作流全部成功和 Release 状态为准；用户明确要求验收安装包或跟踪至公开时，必须继续检查对应产物与结果。用户要求发布完成后关机时，只有全流程成功、安装包及更新清单完成并正式公开后才能关机，不能用构建启动替代完成。

> 已公开版本的 Tag、Release 与安装包绝不改写；没有用户明确授权，也不能更新已推送的未公开标签。

#### 未公开同版本续发

用户明确要求继续同一个尚未公开版本时，先取消其余发布流程，核对该标签没有公开 Release 或安装包，并记录远端标签引用的准确旧对象 SHA。新源码与版本资料应在同一提交，默认分支保持正常快进；仅对目标未公开标签使用限定引用和准确旧 SHA 的 `force-with-lease`，远端引用不符时停止，不强推默认分支，也不以无条件 `--force` 覆盖。

重新绑定后按新目标 SHA 重新运行源码 CI 与发布门禁，核验同标签、同 SHA、同次尝试的检查和产物。旧目标的成功检查、安装包或前端产物不能冒充新目标证据；符合严格祖先要求的可信完整检查仍可经核验作为增量基线。已公开版本不适用这一例外。

### 方式 B：手动发布

1. 打开 https://github.com/Tenney95/AI-Canvas-tauri/releases/new
2. Tag 填 `vX.Y.Z`，Release title 填 `AI Canvas vX.Y.Z`
3. 上传以下文件到 Assets：
   - `AI Canvas_X.Y.Z_x64-setup.exe`（安装包）
   - `AI Canvas_X.Y.Z_x64-setup.exe.sig`（签名）
   - `latest.json`（版本描述）
4. 使用 `.release-notes.md` 的正文填写 Release notes，点击 **Publish release**

> 手动发布时必须上传 `latest.json`，否则自动更新会报 `Could not fetch a valid release JSON`。

## 第七步：验证更新

### 7.1 本地验证

1. 安装目标版本的上一版本
2. 重新构建安装包并安装
3. 打开「关于 → 检查更新」→ 确认显示新版后选择更新 → 核对下载大小、重启后版本与原项目
4. 下载完成后应用自动重启至新版本

### 7.2 验证要点

- 控制台输出 `[Updater] 发现新版本 vX.Y.Z，开始下载...`
- 进度条显示下载进度
- 下载完成后自动安装并重启
- 重启后版本号显示为新版本
- 如果在已是最新版的机器上打开，输出 `当前已是最新版本`
- GitHub Release 的名称和正文与审阅稿一致
- GitHub Release 不是草稿或预发布版本
- Release Assets 包含目标平台安装包、签名文件和 `latest.json`

### 7.3 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `开发模式，跳过更新检查` | `npm run tauri dev` 运行 | 正常，打包后自动不跳过 |
| `Could not fetch a valid release JSON` | `latest.json` 未上传到 Release Assets | 手动上传 |
| `pubkey is not valid` / 签名验证失败 | 本地构建用的 key 与 GitHub Release 的签名不匹配 | 确保用同一密钥对 |
| `failed to decode secret key` | 环境变量未设置或 base64 含换行符 | `Get-Content -Raw` 后加 `.Trim()`，并设置密码 |
| `failed to decode base64 secret key` | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 未设置 | 检查密码是否与生成密钥时一致 |
| Release 的 `publish` 未启动 | 同标签、同 SHA 的计划检查未成功、增量基线不可信，或前端产物缺失 | 查看 Quality gate 与对应标签 CI；已公开版本另发补丁，用户明确要求继续未公开同版本时按旧引用保护规则更新并重检 |
| 默认分支实际发布未启动 | 标签运行未完成转交，或手动运行分支／标签错误 | 查看标签 dispatcher；仅对未公开标签，从默认分支手动启动并明确填写目标 tag |
| CI 中 lint 范围不符 | 执行未使用冻结计划，或工作流／配置不一致 | 核对实际模式、清单及 `Frontend quality`；全量必须全仓，增量必须执行选中项，不能把未执行当成功 |
